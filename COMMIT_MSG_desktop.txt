feat(desktop): act on the machine it already watches

Phase 8 taught Jarvis to SENSE the desktop -- active app, window title, idle
time, screen OCR, all feeding the World Model -- and gave it no way to ACT on
any of it. Nine tools close that asymmetry: list_windows / take_screenshot /
read_clipboard (READ) and focus_window / close_window / launch_app / set_volume
/ media_key / write_clipboard (WRITE). 38 -> 47 tools.

THE WINDOW-HANDLE LOCK mirrors the entity-id lock and binds harder. A concrete
handle on focus/close must trace to a list_windows result in THIS plan: an
entity id is a readable name, so a guessed light.bedroom is at least wrong in a
way a person might notice, while a guessed 4654610 is not. Handles are also
RECYCLED, so close_window carries the title it was approved for and refuses if
the live window no longer matches -- the string on the card is the string the
tool checks, not decoration. It sends WM_CLOSE, never a kill, so an app with
unsaved work still prompts.

launch_app resolves a NAME against the Start Menu registry and has no path,
argument or command parameter, so its reachable surface is exactly the
applications this user installed -- the property run_command cannot have.
take_screenshot returns a PATH and never bytes, because a tool result flows
into planner and summary prompts.

ctypes rather than the spec'd PowerShell helper: the host here is Python, so
there is no subprocess to supervise and -- the real argument -- no shell to
inject into. Two Win32 bugs the live probe found that no amount of reading
would have: COM success is hr >= 0 (SetMute returns S_FALSE when the device is
already in the requested state), and an undeclared ctypes restype defaults to
32-bit c_int, truncating HANDLEs on Win64 -- GetClipboardData segfaulted the
process, and OpenProcess was the same bug waiting for a busier machine.

Two defects found by testing rather than reasoning. The feature's own plan rule
was unresolvable: close_window requires `title`, so rule 25 tells the model to
make both fields PENDING, but the resolver refuses any step with more than one
placeholder key -- every such plan burned an LLM replan on a fully resolvable
step, and only the test that drives the real graph could see it. And the gate
tier ordering was backwards: `open` is a nav cue in ground_origins, so
browse_intent claimed 5 of 6 installed-app phrasings and "open calculator"
audited as "the user named a website".

Sub-toggles split five ways rather than the spec'd four: grouping "turn the
volume down" with "read what I just copied" forces a user who wants the first
to grant the second. Closing windows, the clipboard and screenshots each need
their own deliberate click and all three default OFF. Both /api/desktop routes
are denied on the remote surface -- a phone that could flip allow_clipboard on
is a phone that can read whatever was last copied.

Gates: 82 tests; 16/16 behavioural changes falsified by reverting in place;
21/21 runtime checks on the real main.py lifespan, including an unapproved
close against a REAL window that stayed open; gate recall 21/21 with 1/10
control cost. Live acceptance is user-driven and outstanding.
