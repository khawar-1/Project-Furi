fix(browser): a page is not a response — quote what the submit changed

An approved add-to-cart on junaidjamshed.com completed correctly and reported
~1800 chars back, of which ~220 were the confirmed facts. The rest was the
product page's own prose — the navigation menu, the breadcrumb, the fragrance
notes — presented as "The page shows:".

ROOT CAUSE: browse_commit's `response_text` was the WHOLE post-submit page's
prose (observation.page_text, clipped at 1500). That was written on 2026-07-18
against the-internet.herokuapp.com/upload, whose entire visible text is
"File Uploaded! / dummy_upload.txt" — so the clip never bit and the quote was
always the confirmation. Worse: a Shopify cart-add is an in-page fetch, so the
page never navigates and what came back was the page the form was submitted
FROM. It carried no evidence the submit had worked — grounding theatre.

CLIPPING HARDER WOULD HAVE BEEN MEASURABLY WORSE. The navigation chrome sits at
the TOP of a page's prose, so a smaller budget keeps "WOMEN / MEN / FRAGRANCE &
BEAUTY" and drops whatever confirmation follows it. The budget was never the
problem: "the page's text" is not "the site's response", and no cap converts one
into the other.

So the predicate is asked directly, in code (commit_flow._response_prose): which
lines are NEW since the page the user approved? perform() observes once before
arming (after verify_commit, so a mismatched form pays nothing) and diffs
line-sets. A form that navigates diffs its shared chrome away and keeps the
"Thank you"; an AJAX submit yields nothing, which is the honest answer. An
inline error ("Please enter a valid email") is new, and is the case a user most
needs to see. No LLM — every line returned is a slice of the observation (the
extract.py property). Without a baseline it falls back to _page_moved (did we
navigate?), failing toward brevity rather than toward the dump.
MEASURED on the incident's own page text: 1832 -> 321 chars (82% less), with the
2026-07-18 upload grounding preserved in both tiers.

Two things the measurement caught that reasoning did not:
  * the first cut returned the bare bag counter "3" ("The page shows: 3"). A
    length floor would be the wrong instrument — it would drop "Posted!" (7
    chars) too — so the floor is having WORDS (_RESPONSE_WORD_RE, one run of
    two or more letters).
  * the head claimed 'The site responded: **JANAN SPORT - 100ml**' about a page
    we never left. It now reads "The page stayed on ..." unless page_changed,
    which rides through planner._record_browse_commit and the tool output to the
    renderer. Same class of overclaim as reporting an unconfirmed submit as a
    failure (2026-08-01).

WHY 40+ GREEN TESTS NEVER SAW IT: every fake in test_browser_commit.py returned
a tiny confirmation ("Posted!", "Application 1 received", "Added to cart"), and
StubCommitSession.page was a bare object() — structurally incapable of
expressing "the page before the submit" versus "the page after". The fake now
models the contract. Same shape as the 2026-08-01 FakeBrowser whose new_page()
handed back one shared page object, and as the 2026-07-30 bulk tests that all
drove the singular tool.

Also records a FALSIFIED recommendation. Google Custom Search was proposed here
as the highest-leverage config change (it is the one provider in the chain that
spell-corrects). Verified against Google's own docs while actually setting one
up: "Search the entire web" was DISCONTINUED in March 2026, the Custom Search
JSON API is "closed to new customers", and it RETIRES 1 Jan 2027 — so a new
install cannot use it at all. The code path is kept on purpose (an engine
created before the cut still works until retirement, and unset makes
_google_cse_search a no-op), but .env.example and config.py now say plainly not
to repeat the trip. What actually covers the misheard-domain case is
did_you_mean.py's deterministic title-derived tier, in code and measured.

Tests: +6 test_browser_commit.py (the incident end-to-end through perform with
the storefront prose, asserting the nav menu is absent and page_changed is
False; a navigating submit still quotes the server; the new-prose, counter,
no-baseline and bound matrices), +2 test_plan_rendering.py (the confirmation
renders under 500 chars against the incident's 1832; the head claims a response
only when the page moved). Every behavioural test was proven to FAIL by
reverting the specific line IN PLACE — 5 on the diff, 1 on the word floor, 1 on
the head.

HONEST LIMIT: the diff is line-level, so a page that rewrites a line
cosmetically (a rotating banner, a timestamp) contributes noise, bounded by
_COMMIT_RESPONSE_MAX_CHARS = 400 and the word floor. A site that confirms ONLY
by a counter now says nothing in the quote — the header's confirmed facts (the
interceptor observed the approved request leave) carry it instead, which is the
stronger evidence anyway.
